🐳 Docker

Building, storing and connecting containers
01What is a multi-stage Dockerfile? Why do we use it?

What is it?

A multi-stage Dockerfile uses multiple FROM instructions to separate application building from the final runtime image.

Why do we use it?

  • Reduce the final Docker image size.
  • Remove build tools and unnecessary dependencies from the runtime image.
  • Reduce the attack surface.
  • Improve image transfer and deployment efficiency.

Real-world example

Suppose your company has a Java Spring Boot application. Maven and the JDK are required to build it, but the application only needs a Java runtime to execute.

# Stage 1: Build
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# Stage 2: Runtime
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Interview-ready answer:

"In our project, we use multi-stage Dockerfiles to build the application in one stage and copy only the required artifact into a lightweight runtime image. This reduces image size and avoids shipping build tools into production."

02What are the different types of Docker volumes?

What is it?

Docker provides several ways to persist or share data with containers.

Storage type Description Common use
Named volume Docker-managed storage with an explicit name Database persistence
Anonymous volume Docker-managed volume without a user-defined name Temporary or container-specific persistent storage
Bind mount Maps a host directory or file into a container Development, configuration
tmpfs mount Stores data in host memory on Linux Temporary sensitive data

Real-world example

Your company runs a PostgreSQL container. If the container is removed, database data should remain available.

docker volume create postgres-data

docker run -d \
  --name postgres \
  -e POSTGRES_PASSWORD=example \
  -v postgres-data:/var/lib/postgresql/data \
  postgres:16

The named volume persists independently of the container.

Interview-ready answer:

"We primarily use named volumes for persistent container data and bind mounts when a container needs access to specific host files. For temporary in-memory data, we can use tmpfs mounts."

Important: A named volume alone is not a backup strategy or a high-availability solution.

03What are the different types of Docker networks?

What is it?

Docker networking allows containers to communicate with each other, the host and external systems.

Network driver Purpose
Bridge Communication between containers on the same Docker host
Host Container shares the host's network namespace
None Disables normal container networking
Overlay Connects containers or services across Docker hosts, commonly in Swarm
Macvlan Assigns containers MAC addresses on the physical network
IPvlan Provides network integration using the host's underlying network interface

Real-world example

A frontend application needs to communicate with a backend API.

docker network create app-network

docker run -d \
  --name backend \
  --network app-network \
  my-backend:latest

docker run -d \
  --name frontend \
  --network app-network \
  my-frontend:latest

On the user-defined bridge network, the frontend can resolve the backend container by the hostname backend.

Interview-ready answer:

"In our development environment, we commonly use user-defined bridge networks for communication between application containers. Overlay networking is useful for multi-host container environments, while host networking is used when direct access to the host network is required."

☸️ Kubernetes / AWS EKS

Application health, AWS permissions and scheduling
04What are Probes in Kubernetes?

What is it?

Kubernetes probes check the condition of containers and determine whether they should receive traffic or be restarted.

Probe Purpose Failure behavior
Liveness Checks whether the container needs restarting Restarts the container
Readiness Checks whether the container can receive traffic Marks the Pod unready
Startup Checks whether the application has started successfully Delays liveness/readiness checks until startup succeeds

Real-world example

Your Java application takes 60 seconds to start.

Without proper probes, Kubernetes might restart it before initialization completes.

containers:
  - name: payment-api
    image: payment-api:v1

    startupProbe:
      httpGet:
        path: /health/startup
        port: 8080
      periodSeconds: 5
      failureThreshold: 24

    readinessProbe:
      httpGet:
        path: /health/ready
        port: 8080
      periodSeconds: 5

    livenessProbe:
      httpGet:
        path: /health/live
        port: 8080
      periodSeconds: 10

The startup probe allows up to approximately 120 seconds for startup.

Interview-ready answer:

"We configure startup, readiness and liveness probes to handle application startup, traffic readiness and recovery from unhealthy states. Readiness prevents traffic from reaching an unready Pod, while liveness can restart an unhealthy container."

05What is IRSA (IAM Roles for Service Accounts)?

What is it?

IRSA allows Kubernetes Pods running in Amazon EKS to access AWS services using IAM roles associated with Kubernetes ServiceAccounts.

Why do we use it?

  • Avoid storing long-lived AWS access keys inside containers.
  • Give applications only the AWS permissions they require.
  • Separate application permissions from worker-node IAM permissions.

Real-world example

A backend application running in EKS needs to read files from an S3 bucket.

Instead of putting AWS credentials in the application, we associate a dedicated IAM role with its Kubernetes ServiceAccount.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: s3-reader
  namespace: production
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/eks-s3-reader

Then reference it in the Pod specification:

spec:
  serviceAccountName: s3-reader
  containers:
    - name: backend
      image: backend:v1

The IAM role trust policy must allow the correct EKS OIDC provider and ServiceAccount identity.

Interview-ready answer:

"In our EKS environment, we use IRSA to assign application-specific AWS permissions to Pods through Kubernetes ServiceAccounts. For example, an application requiring S3 read access receives an IAM role with only the necessary S3 permissions."

Additional interview point: EKS Pod Identity is another AWS-supported approach to granting Pods AWS permissions.

06What are Taints and Tolerations?

What is it?

Taints are applied to Kubernetes nodes, while tolerations are configured on Pods.

Together, they control which Pods are permitted to run on tainted nodes.

Why do we use them?

To keep certain workloads away from nodes unless those workloads explicitly tolerate the restriction.

Real-world example

Your company has dedicated nodes for critical production applications.

Apply a taint:

kubectl taint nodes worker-1 \
  workload=critical:NoSchedule

Add a toleration to the critical application's Pod:

tolerations:
  - key: workload
    operator: Equal
    value: critical
    effect: NoSchedule

Three important taint effects:

  • NoSchedule — prevents new Pods without matching tolerations from scheduling.
  • PreferNoSchedule — Kubernetes tries to avoid scheduling non-tolerating Pods.
  • NoExecute — can evict existing Pods that do not tolerate the taint.

Interview-ready answer:

"We use taints and tolerations to restrict scheduling on dedicated nodes. For example, critical workloads can tolerate a taint that prevents ordinary workloads from being scheduled there."

Important: Tolerations allow scheduling but do not guarantee placement. Use node affinity or node selectors when Pods must target specific nodes.

🏗️ Terraform / DevSecOps

Drift, linting, security and reusable infrastructure
07What is Terraform Drift?

What is it?

Terraform drift occurs when the actual infrastructure differs from the configuration Terraform is intended to manage.

Why does it happen?

  • Manual changes through the AWS Console.
  • Changes made using AWS CLI or another automation tool.
  • Infrastructure changes made outside Terraform.

Real-world example

Terraform manages an EC2 instance with type t3.medium.

An engineer manually changes the instance to t3.large through the AWS Console.

Terraform configuration still specifies t3.medium.

Run:

terraform plan

Terraform refreshes its view of managed resources and can detect the difference.

The plan may propose changing the instance type back to t3.medium.

Interview-ready answer:

"In our project, we use Terraform plan in our CI/CD workflow to identify unexpected infrastructure changes. When drift is detected, we review whether the manual change should be reverted or incorporated into Terraform code."

Additional point: A saved Terraform plan should be reviewed before applying changes. Never automatically revert production infrastructure without assessing the impact.

08What is TFLint, and why is it used?

What is it?

TFLint is a Terraform linter that identifies potential problems in Terraform configurations.

Why do we use it?

  • Detect provider-specific configuration issues.
  • Identify deprecated or invalid configuration patterns.
  • Enforce configurable coding standards.
  • Catch certain problems before deployment.

Real-world example

Your team manages AWS infrastructure using Terraform and wants to detect issues during pull-request validation.

tflint --init
tflint --recursive

Example configuration:

plugin "aws" {
  enabled = true
  version = "0.38.0"
  source  = "github.com/terraform-linters/tflint-ruleset-aws"
}

The AWS plugin provides AWS-specific linting rules.

Interview-ready answer:

"We integrate TFLint into our Terraform validation pipeline to detect configuration issues and enforce coding standards before infrastructure changes are merged."

Important: TFLint complements terraform validate; it does not replace it.

09What is Checkov, and how does it help?

What is it?

Checkov is an infrastructure-as-code security scanning tool.

It scans Terraform and other supported infrastructure configurations for security and compliance misconfigurations.

Why do we use it?

  • Identify publicly exposed resources.
  • Detect missing encryption configurations.
  • Check security group rules.
  • Enforce security policies before deployment.

Real-world example

A developer creates an AWS security group that permits SSH access from anywhere.

resource "aws_security_group" "example" {
  name = "example-sg"

  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

Checkov can flag this as a security risk.

Run:

checkov -d .

Interview-ready answer:

"We use Checkov in our CI/CD pipeline to scan Terraform configurations for security misconfigurations before deployment. For example, it helps detect overly permissive security groups and missing encryption settings."

Interview follow-up: TFLint vs Checkov

TFLint Checkov
Terraform linting IaC security scanning
Configuration quality Security and compliance
Provider-specific rules Security policies and checks
Helps prevent configuration mistakes Helps prevent insecure deployments
10How many Terraform modules have you created or used in your project?

This is an experience-based interview question. The interviewer wants to understand your actual hands-on Terraform work, not simply hear a number.

What is a Terraform module?

A Terraform module is a reusable collection of Terraform configuration files that manages a set of related infrastructure resources.

Why do we use modules?

  • Reuse infrastructure configurations.
  • Standardize deployments across environments.
  • Reduce duplication.
  • Simplify infrastructure maintenance.
  • Provide consistent configuration patterns.

Real-world example

Suppose a project uses this repository structure:

terraform/
├── main.tf
├── providers.tf
├── variables.tf
├── outputs.tf
├── environments/
│   ├── dev.tfvars
│   ├── qa.tfvars
│   └── prod.tfvars
└── modules/
    ├── vpc/
    ├── security-group/
    ├── ec2/
    ├── alb/
    ├── eks/
    ├── iam/
    ├── s3/
    ├── rds/
    ├── sns/
    └── sqs/

This is an illustrative repository structure, not a fixed or required module count. The root configuration is also a module. Additional child modules may be created for SNS, SQS, networking, or other services whenever requirements justify them.

Example module invocation:

module "vpc" {
  source = "./modules/vpc"

  vpc_cidr = "10.0.0.0/16"
  environment = "dev"
}

Interview-ready answer:

“In our project, we build and maintain AWS infrastructure using reusable Terraform modules. Our responsibilities cover networking (VPCs, subnets, route tables and security groups), EC2 servers, application load balancers, EKS clusters, IAM roles and policies, S3 buckets, databases, and messaging services such as SNS and SQS.

There is no fixed number of modules. When a new requirement comes in, we first check whether an existing module can be reused or extended. If the component needs its own reusable configuration, we create a child module and call it from the root module, passing inputs and consuming outputs. We focus on consistent, maintainable infrastructure across environments rather than quoting a module count.”

Only describe services you have actually worked with during an interview.

Possible follow-up questions:

  • What is the difference between root and child modules?
  • How do you pass variables into modules?
  • How do you access module outputs?
  • How do you manage module versions?
  • How do you structure environments?
  • How do you handle remote Terraform state?
